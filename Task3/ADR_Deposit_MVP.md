### **Решение**

#### **Архитектурное видение**

Для реализации MVP открытия депозитов онлайн принято решение о **частичном переходе на микросервисную архитектуру** с созданием нового домена "Система депозитов", который будет работать параллельно с существующим монолитом интернет-банка.

#### **Предпосылки выбора технологий**

**Выбор Java версии:**

На ноябрь 2025 года доступны следующие LTS релизы Java:
- **Java 17** (сентябрь 2021) - минимальная версия для Spring Boot 3.x, устаревает
- **Java 21** (сентябрь 2023) - стабильный LTS с 2+ годами в production, поддержка до 2029 года ✅
- **Java 25** (сентябрь 2025) - новейший LTS, слишком свежий для критичных банковских систем

**Решение: Java 21 LTS**

**Обоснование выбора Java 21:**
1. ✅ **Зрелость:** 2+ года в production, все детские болезни исправлены
2. ✅ **LTS поддержка:** До 2029 года (Oracle), до 2032 года (другие вендоры)
3. ✅ **Performance:** Virtual threads (Project Loom) для high-concurrency приложений (P1, P4)
4. ✅ **Spring Boot готовность:** Полная поддержка в Spring Boot 3.2+ с оптимизациями
5. ✅ **Экосистема:** Все основные библиотеки совместимы
6. ✅ **Совместимость:** Система кол-центра банка может использовать Java 11+, легко мигрирует на 21

**Почему не Java 17:**
- ❌ Устаревает (выпущен 4 года назад)
- ❌ Нет virtual threads (критично для производительности P1, P4)
- ❌ Меньше оптимизаций GC

**Почему не Java 25 (пока):**
- ❌ Слишком свежий релиз (сентябрь 2025) для критичного MVP банка
- ❌ Spring Boot 4.0 только что вышел (ноябрь 2025), нет достаточного production опыта
- ⚠️ Рекомендуется для следующего этапа развития (через 6-12 месяцев)

**Spring Boot версия: 3.4+ (стабильная) / 3.5+ (latest)**
- Spring Boot 3.4 - стабильная версия с полной поддержкой Java 21
- Spring Boot 4.0 (ноябрь 2025) - для будущих проектов после стабилизации

#### **Ключевые архитектурные решения:**

**1. Микросервисная архитектура для нового функционала**

Вместо доработки монолита интернет-банка создается новый кластер микросервисов:
- **Deposit Service** - управление заявками на депозиты
- **Rate Management Service** - управление справочником ставок
- **Notification Service** - отправка SMS-уведомлений

**Обоснование:**
- ✅ Уход от зависимости от подрядчика (S3, S5)
- ✅ Возможность независимого развития и масштабирования (R5, P4)
- ✅ Использование Java 21 LTS с **virtual threads** для высокой производительности (P1, P4)
- ✅ Экспертиза в Java-стеке в банке (команда АБС) (S1, S2)
- ✅ Подготовка к будущей интеграции с Kafka (+R1, +R2)

**Virtual threads (Java 21):**
- Позволяют эффективно обрабатывать тысячи одновременных запросов без блокировки потоков
- Идеально для I/O операций (вызовы к АБС, БД, внешним API)
- Простая активация в Spring Boot 3.2+: `spring.threads.virtual.enabled=true`

**2. API Gateway для маршрутизации**

Введение API Gateway (Nginx/Kong) между фронтендом и бэкендом для:
- Маршрутизации запросов между монолитом и микросервисами
- Централизованной аутентификации и авторизации (+R3)
- Балансировки нагрузки (P2)
- Управления rate limiting

**3. Новое SPA-приложение для депозитов**

Создание нового фронтенда на React вместо доработки легаси ASP.NET MVC:
- ✅ Современный UX для клиентов (U1, U2, U3)
- ✅ Независимость от подрядчика (S3)
- ✅ Возможность быстрых итераций

**4. АБС API Layer**

Создание тонкого REST API слоя над АБС для:
- Защиты базы данных от прямого доступа (R3, +R5)
- Стандартизации интеграций
- Read-Only операций для снижения рисков

**5. Отдельная база данных PostgreSQL**

Для системы депозитов используется собственная БД:
- ✅ Независимость от перегруженной БД АБС (R3)
- ✅ Использование технологии с экспертизой в банке (+R7, S1)
- ✅ Возможность горизонтального масштабирования (R5, P4)

**6. Асинхронные уведомления**

Notification Service работает независимо:
- ✅ Уход от зависимости от SMS-функционала в ядре интернет-банка (S5)
- ✅ Возможность переиспользования для других каналов (F4)

**7. Ручная обработка в MVP**

Для MVP сотрудники бэк-офиса:
- Видят заявки в веб-админке
- Вручную открывают депозиты в АБС (F8)
- Меняют статус заявки

**Обоснование MVP подхода:**
- ✅ Быстрый вывод на рынок (6 месяцев)
- ✅ Минимизация рисков интеграции с АБС
- ✅ Возможность тестирования процесса на реальных клиентах

#### **Технологический стек**

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| Deposit Service | **Java 21 LTS** + Spring Boot 3.4+ | Зрелый LTS с поддержкой до 2029 года, virtual threads для производительности (P1, P4), экспертиза в банке (S1, S2) |
| Rate Service | **Java 21 LTS** + Spring Boot 3.4+ | Единообразие стека, независимость от подрядчиков (S3), стабильная версия для production |
| Notification Service | **Java 21 LTS** + Spring Boot 3.4+ | Единообразие стека, уход от зависимости от ядра ИБ (S5), готовность к Spring Boot 4 в будущем |
| Deposit DB | PostgreSQL 15+ | Экспертиза в банке (система кол-центра), допускается для микросервисов (+R7) |
| API Gateway | Nginx + Kong | Легковесное решение, готовность к Kafka в будущем (+R1), балансировка (P2) |
| Frontend | React 18 + TypeScript | Современный стек, единообразие с сайтом, простота для пользователей (U1, U2) |
| АБС API Layer | **Java 21 LTS** | Экспертиза в Java у специалистов АБС, защита от перегрузки (R3, +R5), совместимость с новыми сервисами |

**Примечание по выбору версий:**
- **Java 21 (сентябрь 2023)** - проверенный LTS релиз с 2+ годами в production, поддержка до 2029 года
- **Spring Boot 3.4+** - стабильная версия с полной поддержкой Java 21, включая virtual threads
- **Альтернатива:** Java 25 LTS (сентябрь 2025) + Spring Boot 4.0 (ноябрь 2025) для будущих проектов, но слишком свежие для критичного банковского MVP
- **Не рекомендуется:** Java 17 (устаревает), Spring Boot 2.x (EOL)

#### **Интеграции**

**Синхронные (REST API):**
- Интернет-банк → Deposit Service (подача заявки)
- Deposit Service → Rate Service (расчет ставок)
- Rate Service → АБС API (данные клиента)
- Deposit Service → АБС API (проверка счетов)
- Deposit Service → Notification Service (отправка SMS)
- Система кол-центра → Deposit Service, Rate Service (просмотр заявок и ставок)

**Асинхронные (в целевом решении через Kafka):**
- В MVP все интеграции синхронные для упрощения

#### **Безопасность**

- HTTPS/TLS для всех внешних каналов (+R3)
- OAuth 2.0 + JWT для аутентификации через API Gateway
- Read-Only доступ к АБС БД через API Layer (+R5)
- Изоляция данных депозитов в отдельной БД
- Rate limiting на API Gateway

#### **Масштабируемость**

- Deposit Service, Rate Service, Notification Service поддерживают горизонтальное масштабирование (R5, P4)
- Балансировка нагрузки через API Gateway (P2)
- Кэширование справочных данных (ставки) в Redis для оптимизации (P5, U3)
- АБС остается с вертикальным масштабированием (ограничение Oracle БД)

### **Альтернативы**

#### **Альтернатива 1: Доработка существующего монолита интернет-банка**

**Описание:** Добавить функционал депозитов в существующий ASP.NET MVC монолит.

**Преимущества:**
- Быстрее в краткосрочной перспективе
- Нет необходимости в новой инфраструктуре
- Использование существующей аутентификации

**Недостатки:**
- ❌ Зависимость от подрядчика для обновления ядра (S3, S5)
- ❌ Невозможность использования Kafka (+R2)
- ❌ Риски для стабильности всего монолита
- ❌ Сложность масштабирования (P4)
- ❌ Устаревший технологический стек (.NET 4.5)

**Решение:** Отклонена из-за стратегической цели ухода от зависимости от подрядчика.

#### **Альтернатива 2: Полная интеграция с АБС через API в MVP**

**Описание:** Сразу реализовать автоматическое открытие депозитов в АБС через API.

**Преимущества:**
- Полная автоматизация с первого дня
- Нет ручной работы бэк-офиса

**Недостатки:**
- ❌ Долгая разработка (9-12 месяцев вместо 6)
- ❌ Высокие риски интеграции с legacy АБС
- ❌ Необходимость тестирования критичных операций
- ❌ Дополнительная нагрузка на перегруженную БД АБС (R3, +R5)

**Решение:** Отложена на целевое состояние (через год). В MVP используется ручная обработка (F8).

#### **Альтернатива 3: Использование существующей системы кол-центра как основы**

**Описание:** Расширить систему кол-центра (Java/Spring Boot/PostgreSQL) для обработки депозитов.

**Преимущества:**
- Уже используется микросервисная архитектура
- Есть экспертиза в команде АБС по Java-стеку

**Недостатки:**
- ❌ Зависимость от подрядчика кол-центра
- ❌ Смешивание доменов (CRM и депозиты)
- ❌ Риски для работы кол-центра при проблемах

**Решение:** Отклонена из-за нарушения принципа разделения доменов.

### **Недостатки, ограничения, риски**

#### **Недостатки решения:**

1. **Дублирование данных:**
   - Данные о заявках хранятся в Deposit DB
   - Открытые депозиты хранятся в АБС
   - Необходима синхронизация статусов

2. **Ручная работа в MVP:**
   - Сотрудники бэк-офиса выполняют двойную работу (админка + АБС)
   - Риск человеческих ошибок
   - Невысокая пропускная способность

3. **Дополнительная сложность инфраструктуры:**
   - Новые компоненты требуют мониторинга
   - Необходимость обучения команд
   - Операционные расходы на поддержку

#### **Ограничения:**

1. **Текущая неготовность к полному горизонтальному масштабированию:**
   - Интернет-банк работает на одной группе серверов
   - Требуется постепенная миграция на микросервисы (P4, R5)

2. **Зависимость от доступности АБС:**
   - При недоступности АБС невозможен расчет персональных ставок (F3)
   - Невозможна проверка счетов клиента

3. **Отсутствие событийной архитектуры:**
   - В MVP все интеграции синхронные
   - Kafka запланирована только в целевом решении (+R1, +R2)

4. **Ограничения для новых клиентов:**
   - Новые клиенты должны проходить идентификацию в отделении (+R4)
   - Полностью онлайн-процесс невозможен по требованиям регулятора

#### **Риски:**

| Риск | Вероятность | Влияние | Меры митигации |
|------|-------------|---------|----------------|
| **R1:** Сопротивление команды монолита переходу на микросервисы | Средняя | Высокое | Постепенная миграция, обучение команды, вовлечение в проектирование (S3, S4) |
| **R2:** Проблемы с производительностью АБС API Layer | Средняя | Высокое | Read-Only доступ, кэширование, мониторинг нагрузки (R3, +R5) |
| **R3:** Сложности интеграции с legacy АБС | Высокая | Критическое | Тщательное тестирование, rollback plan, фазированный запуск |
| **R4:** Недостаточная пропускная способность бэк-офиса в MVP | Средняя | Среднее | Автоматизация в целевом решении через 6 месяцев (F8) |
| **R5:** Рост операционных расходов на новую инфраструктуру | Низкая | Среднее | Использование существующей инфраструктуры, постепенное масштабирование (S1) |
| **R6:** Проблемы с синхронизацией данных между системами | Средняя | Высокое | Четкое управление статусами, логирование всех изменений (R6) |
