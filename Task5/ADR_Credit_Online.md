### **Решение**

#### **Архитектурное видение**

Для реализации онлайн кредитования с предодобренными предложениями используется **микросервисная архитектура** с переиспользованием существующих систем (Кредитный конвейер, Система скоринга) и добавлением нового оркестратора - **Credit Gateway Service**.

Ключевая идея: **не переписываем кредитный движок**, а создаем **тонкий слой оркестрации** для онлайн-каналов.

#### **Технологический выбор**

Все новые компоненты используют **Java 21 LTS + Spring Boot 3.4+** для:
- ✅ Единообразия стека с Deposit Service, Rate Service (Task 3)
- ✅ Возможности использования virtual threads для high-concurrency
- ✅ Совместимости с Кредитным конвейером (Java + Camunda)
- ✅ Поддержки до 2029 года

---

#### **Ключевые архитектурные решения:**

**1. Credit Gateway Service - оркестратор кредитного процесса**

Новый микросервис, который является **единой точкой входа** для онлайн-заявок на кредит:

**Компоненты:**
- **Credit API** - REST API для приема заявок и показа статусов
- **Pre-Approval Engine** - фоновый процесс расчета предодобренных предложений
- **Credit DB (PostgreSQL)** - хранение заявок, предодобрений, статусов

**Ответственность:**
- Прием заявок с фронтенда (сайт, интернет-банк)
- Показ предодобренных предложений клиентам (F6)
- Отправка заявок в Кредитный конвейер (real-time)
- Отслеживание статусов заявок
- Отправка SMS-уведомлений

**Обоснование:**
- ✅ Единая точка входа для онлайн-каналов (S3)
- ✅ Изоляция онлайн-логики от legacy конвейера
- ✅ Возможность быстрых итераций без затрагивания конвейера
- ✅ Кэширование предодобрений для быстрого показа (P1)

---

**2. Pre-Approval Engine - фоновый расчет предодобренных предложений**

**Механизм работы:**

1. **Scheduler запускается ночью** (например, в 02:00):
   - Минимальная нагрузка на системы банка
   - Не перегружает Систему скоринга в рабочие часы (R4)

2. **Выбор кандидатов:**
   - Активные клиенты с положительным балансом
   - Без текущих просрочек по кредитам
   - Без активных кредитных заявок

3. **Расчет предодобрения:**
   - Запрос скоринга для клиента (Система скоринга → БКИ + АБС)
   - Определение максимальной суммы кредита на основе скоринга
   - Расчет персональной ставки
   - Сохранение в Credit DB с TTL=30 дней

4. **Показ клиенту:**
   - Клиент заходит в интернет-банк
   - Credit Gateway показывает актуальное предодобрение из кэша (P1)
   - Если предодобрение устарело - не показывается

**Обоснование:**
- ✅ Защита скоринга от перегрузки - расчеты ночью (R4)
- ✅ Быстрый показ предложений клиенту - из кэша (P1)
- ✅ Актуальность предложений - TTL 30 дней
- ✅ Клиент не ждет скоринг при входе в ИБ

---

**3. Real-time интеграция с Кредитным конвейером**

**Текущая проблема (AS-IS):**
- Заявки передаются из АБС в Конвейер **раз в день** (batch)
- Клиент ждет решения **неделю**
- Невозможно ускорить batch-интеграцию (+R7)

**Решение (TO-BE):**

Добавляем **REST API в Кредитный конвейер**:
```
POST /api/applications
```

**Поток:**
1. Credit Gateway получает заявку от клиента
2. Credit Gateway вызывает REST API Кредитного конвейера (real-time)
3. Conveyor API создает новый BPMN процесс в Camunda
4. Кредитный специалист видит заявку **немедленно**
5. При изменении статуса Конвейер отправляет webhook в Credit Gateway
6. Credit Gateway обновляет статус и уведомляет клиента

**Обоснование:**
- ✅ Решение за 1 день вместо недели (P3)
- ✅ Минимальные изменения в Конвейере - только API endpoint (S3)
- ✅ Вся бизнес-логика остается в Camunda
- ✅ Переиспользование существующей системы

---

**4. Переиспользование Системы скоринга**

Система скоринга используется **без изменений**:
- Pre-Approval Engine вызывает существующий REST API (ночью)
- Credit Gateway вызывает API для новых клиентов с сайта
- Кредитный конвейер вызывает API для детального скоринга (как раньше)

**Защита от перегрузки (R4):**
- Pre-Approval расчеты - ночью
- Rate limiting на стороне Credit Gateway
- Кэширование результатов скоринга в Scoring DB

**Обоснование:**
- ✅ Нулевые изменения в ML модели
- ✅ Переиспользование существующей инфраструктуры
- ✅ Защита от перегрузки через timing и rate limiting

---

**5. Асинхронная модель обработки**

**Eventual consistency:**
- Credit Gateway сохраняет заявку локально (источник правды для онлайн-статусов)
- Кредитный конвейер обрабатывает заявку независимо
- Webhook от конвейера синхронизирует статусы

**Обработка сбоев:**
- Если webhook не дошел - retry механизм (Spring Retry)
- Если конвейер недоступен - заявка в очереди (можно добавить Kafka позже)
- Credit Gateway может polling статуса из конвейера как fallback

**Обоснование:**
- ✅ Отказоустойчивость (R6)
- ✅ Независимость систем
- ✅ Готовность к event-driven архитектуре (+R1 - Kafka)

---

**6. Единообразие UX с депозитами**

Клиент видит **похожий процесс** для депозитов и кредитов:
- Те же UI компоненты (React)
- Та же система дизайна (U1)
- Тот же API Gateway
- Те же SMS-уведомления (Notification Service)

**Обоснование:**
- ✅ Простота для пользователей (U2)
- ✅ Переиспользование компонентов из Task 3
- ✅ Единообразие кодовой базы

#### **Интеграции**

**Синхронные (REST API):**
- Интернет-банк/Сайт → Credit Gateway (подача заявки)
- Credit Gateway → Кредитный конвейер (отправка заявки)
- Credit Gateway → Система скоринга (быстрый скоринг для новых клиентов)
- Credit Gateway → АБС API (данные клиента)
- Pre-Approval Engine → Система скоринга (фоновый расчет)
- Кредитный конвейер → Система скоринга (детальный скоринг)

**Асинхронные (Webhook):**
- Кредитный конвейер → Credit Gateway (изменение статуса заявки)

**Batch (расписание):**
- Pre-Approval Engine запускается ночью (Quartz Scheduler)

---

#### **Безопасность**

- HTTPS/TLS для всех внешних каналов (+R3)
- OAuth 2.0 + JWT для аутентификации через API Gateway
- Read-Only доступ к АБС через API Layer (+R5)
- Rate limiting на Credit Gateway для защиты скоринга (R4)
- Изоляция данных заявок в отдельной БД
- Аудит всех операций с кредитными заявками

---

#### **Масштабируемость**

- Credit Gateway поддерживает горизонтальное масштабирование (R5, P4)
- Pre-Approval Engine может масштабироваться через партиционирование клиентов
- Кредитный конвейер поддерживает горизонтальное масштабирование (уже готов)
- Система скоринга поддерживает масштабирование (уже готова)
- Балансировка нагрузки через API Gateway

### **Альтернативы**

#### **Альтернатива 1: Переписать Кредитный конвейер на микросервисы**

**Описание:** Создать новый кредитный движок вместо использования Camunda.

**Преимущества:**
- Полный контроль над процессом
- Современная архитектура с нуля

**Недостатки:**
- ❌ Очень долгая разработка (12-18 месяцев)
- ❌ Высокие риски потери бизнес-логики
- ❌ Необходимость переобучения кредитных специалистов
- ❌ Дублирование функциональности

**Решение:** Отклонена. Кредитный конвейер работает и содержит критичную бизнес-логику. Переиспользуем.

---

#### **Альтернатива 2: Pre-Approval расчеты в real-time при входе клиента**

**Описание:** Рассчитывать предодобрение "на лету" когда клиент открывает раздел кредитов.

**Преимущества:**
- Всегда актуальные данные
- Не нужен фоновый процесс

**Недостатки:**
- ❌ Долгая загрузка для клиента (скоринг занимает 5-10 сек)
- ❌ Огромная нагрузка на Систему скоринга (R4)
- ❌ Плохой UX (P1)

**Решение:** Отклонена. Фоновый расчет ночью с кэшированием - оптимальное решение.

---

#### **Альтернатива 3: Хранить предодобрения в АБС**

**Описание:** Сохранять предодобрения в АБС вместо отдельной БД.

**Преимущества:**
- Единый источник правды
- Нет дублирования данных

**Недостатки:**
- ❌ Дополнительная нагрузка на перегруженную БД АБС (R3)
- ❌ Сложность изменений в АБС (долгие циклы)
- ❌ Зависимость от команды АБС

**Решение:** Отклонена. Отдельная БД для микросервиса - правильный подход.

### **Недостатки, ограничения, риски**

#### **Недостатки решения:**

1. **Дублирование данных о заявках:**
   - Заявки хранятся и в Credit DB, и в Conveyor DB
   - Необходима синхронизация статусов через webhook
   - Риск десинхронизации при сбоях

2. **Зависимость от доработки Кредитного конвейера:**
   - Необходимо добавить REST API в существующую систему
   - Требуется работа команды конвейера
   - Возможные задержки в разработке

3. **Pre-Approval для ограниченного числа клиентов:**
   - Ночной расчет не охватывает всех клиентов
   - Новые клиенты не получают предодобрений (только после регистрации)
   - Устаревание предодобрений через 30 дней

#### **Ограничения:**

1. **Новые клиенты должны приходить в отделение (+R4):**
   - Полностью онлайн-кредит невозможен по требованиям ЦБ РФ
   - Необходима личная идентификация

2. **Batch интеграция АБС↔Конвейер сохраняется (+R7):**
   - Для заявок из отделений сохраняется старый процесс (раз в день)
   - Только онлайн-заявки идут через real-time API

3. **Ограничения Системы скоринга (R4):**
   - Нельзя запускать массовые скоринги в рабочие часы
   - Ограничение на количество запросов к БКИ (платные API вызовы)

#### **Риски:**

| Риск | Вероятность | Влияние | Меры митигации |
|------|-------------|---------|----------------|
| **R1:** Команда конвейера не может добавить REST API вовремя | Средняя | Критическое | Раннее начало работ, выделение ресурсов, простота API |
| **R2:** Десинхронизация статусов между Credit Gateway и Конвейером | Средняя | Высокое | Retry механизм для webhook, polling как fallback, мониторинг консистентности |
| **R3:** Перегрузка Системы скоринга при pre-approval расчетах | Средняя | Высокое | Ночной timing, rate limiting, постепенный rollout (50% клиентов → 100%) |
| **R4:** Низкая конверсия предодобренных предложений | Средняя | Среднее | A/B тестирование UX, персонализация предложений, маркетинг |
| **R5:** Устаревание предодобрений (TTL 30 дней) | Низкая | Среднее | Клиент может запросить актуальный скоринг при подаче заявки |
| **R6:** Сложность миграции с batch на real-time для кредитных специалистов | Средняя | Среднее | Обучение команды, постепенный переход (сначала только онлайн, потом отделения) |
