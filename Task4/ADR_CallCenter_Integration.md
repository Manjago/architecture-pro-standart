### **Нефункциональные требования**

Архитектурно значимые требования для интеграции кол-центров:

|**№**|**Требование**|
| :-: | :- |
|**NFR-1**|**Удобство использования (U5):** Операторы обоих кол-центров должны иметь доступ к актуальным ставкам для консультирования клиентов|
|**NFR-2**|**Функциональность (F1):** Ставки должны быть актуальными и единообразными во всех каналах (сайт, ИБ, КЦ)|
|**NFR-3**|**Ограничения (+R6):** Партнёрский кол-центр может получать данные только через файлы (SFTP), API-интеграция невозможна|
|**NFR-4**|**Производительность (P1):** Время отклика API для запроса ставок должно быть не более 100-200 мс|
|**NFR-5**|**Надёжность (R1):** Внутренний кол-центр должен работать 24/7 с доступностью 99.9%|
|**NFR-6**|**Надёжность (R6):** Отказоустойчивость критических операций - если выгрузка на SFTP упала, должен быть retry механизм|
|**NFR-7**|**Поддерживаемость (S1, S2):** Использование Java для доработки системы кол-центра банка (есть экспертиза в команде АБС)|
|**NFR-8**|**Поддерживаемость (S3):** Возможность расширения функциональности без зависимости от подрядчика КЦ|
|**NFR-9**|**Безопасность (+R3):** Передача файлов через защищённый канал (SFTP с SSH-ключами)|

### **Решение**

#### **Архитектурное видение**

Для обеспечения доступа кол-центров к актуальным ставкам используется **гибридный подход**:
- **Внутренний кол-центр** - интеграция через REST API (real-time)
- **Партнёрский кол-центр** - интеграция через файлы (batch, 2 раза в день)

Это решение учитывает технические ограничения партнёра (+R6) и обеспечивает оптимальный UX для обоих каналов.

**Технологический выбор:**

Все новые компоненты используют **Java 21 LTS + Spring Boot 3.4+** для:
- ✅ Единообразия стека с Deposit Service и Rate Service (Task 3)
- ✅ Зрелости технологии (2+ года в production)
- ✅ Поддержки до 2029 года
- ✅ Возможности использования virtual threads для оптимизации I/O операций (чтение БД, SFTP)
- ✅ Совместимости с существующей системой кол-центра банка (Java/Spring Boot)

#### **Ключевые архитектурные решения:**

**1. REST API для внутреннего кол-центра**

Rate Management Service предоставляет REST API endpoints:
- `GET /api/rates/deposits` - список всех актуальных ставок
- `GET /api/rates/deposits/{product_id}` - детали по конкретному продукту
- `GET /api/rates/deposits/history` - история изменений (аудит)

**Обоснование:**
- ✅ Real-time доступ к актуальным данным (U5)
- ✅ Единый источник правды (F1)
- ✅ Команда АБС может доработать UI системы КЦ (S1, S2, S7)
- ✅ Быстрый отклик (P1)

**2. Rate Export Service для партнёрского кол-центра**

Новый микросервис (или модуль Rate Service) для экспорта данных:

**Компоненты:**
- **Scheduler:** Quartz Scheduler в Spring Boot
- **Экспорт:** Apache POI для Excel или OpenCSV для CSV
- **SFTP Client:** JSch или Apache Commons VFS
- **Retry механизм:** Spring Retry для отказоустойчивости

**Процесс:**
1. Cron запускается 2 раза в день (08:00, 14:00)
2. Читает актуальные ставки из Rate DB
3. Генерирует файл `deposit_rates_YYYYMMDD_HHMM.csv`
4. Выгружает на SFTP-сервер партнёра
5. Логирует результат, отправляет алерт при ошибке

**Обоснование:**
- ✅ Соответствует ограничению партнёра (+R6)
- ✅ Простота реализации (2 недели разработки)
- ✅ Отказоустойчивость через retry (R6)
- ✅ Асинхронность - не влияет на производительность других систем

**3. Формат файла**

CSV файл со структурой:
```csv
product_id,product_name,term_months,base_rate,min_amount,max_amount,updated_at
DEP001,Накопительный счёт,0,7.5,10000,10000000,2025-11-21T08:00:00Z
DEP002,Депозит 6 месяцев,6,8.0,50000,5000000,2025-11-21T08:00:00Z
DEP003,Депозит 12 месяцев,12,8.5,50000,5000000,2025-11-21T08:00:00Z
```

**Преимущества формата:**
- Простой парсинг для партнёра
- Читаемость человеком
- Малый размер файла
- Excel-совместимость (при необходимости)

**4. Мониторинг и алертинг**

- Мониторинг успешности выгрузок (Grafana dashboard)
- Алерты в Slack/Email при ошибках SFTP
- Логирование всех операций
- Метрики: время генерации файла, размер, успешность

#### **Диаграммы**

См. файлы:
- `C1_Context_CallCenter_Integration.puml` - Диаграмма контекста (C1)
- `C2_Container_CallCenter_Integration.puml` - Диаграмма контейнеров (C2)

#### **Технологический стек**

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| Rate Export Service | **Java 21 LTS** + Spring Boot 3.4+ | Единообразие стека с другими микросервисами, экспертиза в банке (S1, S2), поддержка до 2029 года |
| Scheduler | Quartz Scheduler (встроенный в Spring Boot) | Проверенное решение для cron-задач, нативная поддержка |
| CSV Export | OpenCSV | Легковесная библиотека, совместима с Java 21 |
| SFTP Client | JSch / Apache Commons VFS | Проверенные решения для SFTP, стабильные на Java 21 |
| Retry Logic | Spring Retry | Встроенная отказоустойчивость (R6), часть Spring Boot |
| Monitoring | Prometheus + Grafana | Стандарт в банке для мониторинга |

**Примечание:** Все новые микросервисы используют **Java 21 LTS** для единообразия технологического стека и возможности использования virtual threads для оптимизации производительности (P1).

#### **Интеграции**

**Синхронные:**
- Система кол-центра → Rate Service REST API (real-time)

**Асинхронные (batch):**
- Rate Export Service → SFTP сервер партнёра (2 раза в день)

#### **Безопасность**

- REST API защищён OAuth 2.0 + JWT
- SFTP с SSH-ключами (публичный/приватный) (+R3)
- Сетевая изоляция: Rate Service в DMZ
- Rate limiting на API endpoints
- Аудит всех изменений ставок

### **Альтернативы**

#### **Альтернатива 1: Real-time интеграция с партнёром через VPN**

**Описание:** Настроить VPN-туннель между банком и партнёром для API-доступа.

**Преимущества:**
- Real-time доступ к ставкам
- Единообразие интеграций

**Недостатки:**
- ❌ Партнёр не готов к API-интеграции (+R6)
- ❌ Длительное согласование безопасности
- ❌ Высокие требования к инфраструктуре партнёра
- ❌ Зависимость от доступности канала

**Решение:** Отклонена из-за технических ограничений партнёра.

#### **Альтернатива 2: Email рассылка файлов со ставками**

**Описание:** Отправлять файлы на email партнёра вместо SFTP.

**Преимущества:**
- Простота реализации
- Не требует настройки SFTP

**Недостатки:**
- ❌ Низкая безопасность (чувствительные данные в email) (+R3)
- ❌ Ручной импорт на стороне партнёра
- ❌ Риск потери писем
- ❌ Нет автоматизации

**Решение:** Отклонена из-за требований безопасности.

#### **Альтернатива 3: Общая база данных**

**Описание:** Предоставить партнёру read-only доступ к Rate Database.

**Преимущества:**
- Real-time доступ
- Минимальная разработка

**Недостатки:**
- ❌ Критические риски безопасности
- ❌ Зависимость от доступности БД банка
- ❌ Нарушение изоляции систем
- ❌ Невозможно по корпоративным политикам

**Решение:** Категорически отклонена.

### **Недостатки, ограничения, риски**

#### **Недостатки решения:**

1. **Задержка данных у партнёра:**
   - Ставки обновляются только 2 раза в день
   - Если ставки изменились в 15:00, партнёр узнает об этом только на следующий день в 08:00
   - **Митигация:** Выбор времени выгрузок согласован с бизнесом (утро + после обеда)

2. **Ручная обработка сбоев SFTP:**
   - При проблемах со связью потребуется вмешательство техподдержки
   - **Митигация:** Retry механизм, алертинг, runbook для операторов

3. **Зависимость от инфраструктуры партнёра:**
   - Банк не контролирует SFTP-сервер партнёра
   - **Митигация:** SLA с партнёром, мониторинг доступности

#### **Ограничения:**

1. **Формат файла фиксирован:**
   - Изменение структуры потребует согласования с партнёром
   - Версионирование формата для обратной совместимости

2. **Нет персонализации для партнёрского КЦ:**
   - Партнёр видит только базовые ставки, без персонализации
   - Для персональных предложений клиент должен обратиться напрямую в банк (+R4)

3. **Масштабируемость файлового подхода:**
   - При росте количества продуктов файл может стать большим
   - **Митигация:** Compression (gzip), разбиение на несколько файлов

#### **Риски:**

| Риск | Вероятность | Влияние | Меры митигации |
|------|-------------|---------|----------------|
| **R1:** Партнёр не может настроить SFTP-сервер вовремя | Средняя | Высокое | Начать согласование инфраструктуры на Фазе 1, предоставить инструкции |
| **R2:** Проблемы с доступом к SFTP из сети банка (firewall) | Средняя | Среднее | Тестирование на Фазе 3, работа с InfoSec для открытия портов |
| **R3:** Партнёр неправильно импортирует файлы | Средняя | Среднее | Документация формата, примеры, тестовые файлы, поддержка на старте |
| **R4:** Изменения в системе кол-центра банка заблокированы подрядчиком | Низкая | Высокое | Раннее согласование с подрядчиком КЦ, использование расширяемости системы (S3) |
| **R5:** Файлы со ставками попадают к конкурентам | Низкая | Критическое | SSH-ключи, шифрование канала (+R3), аудит доступа, NDA с партнёром |
| **R6:** Десинхронизация данных между каналами | Низкая | Среднее | Единый источник правды (Rate Service), мониторинг консистентности |

#### **План снижения рисков:**

1. **Предварительная интеграция (Фаза 1-2):**
   - Согласование SFTP-доступа с партнёром
   - Тестовые выгрузки файлов
   - Проверка импорта на стороне партнёра

2. **Документация и обучение:**
   - Спецификация формата файла
   - Runbook для операторов техподдержки
   - Обучение партнёра импорту данных

3. **Мониторинг:**
   - Dashboard с метриками выгрузок
   - Алертинг при сбоях
   - Еженедельный review логов

4. **SLA с партнёром:**
   - Доступность SFTP-сервера 99.5%
   - Время на импорт файла - до 1 часа
   - Ответственность за безопасность данных
